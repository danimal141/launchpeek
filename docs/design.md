# launchpeek 設計方針

コードや [SPEC.md](../SPEC.md) を読めばわかることは書かない。実装の裏にある判断とその理由だけを記す。

## launchctl の出力を信頼しない

launchd には状態取得の公開 API が無い。情報源は `launchctl` の出力テキストと plist で、出力形式を Apple は保証していない。

そのため、パースの失敗は異常ではなく通常の入力として扱う。未知の行や取れない項目はエラーにせず「情報が無い」状態として UI まで渡し、アプリはどんな入力でも落とさない。パーサの正しさは実出力から採取した fixture で担保し、形式が変わったら fixture を足して追随する。

## レイヤ分離はテストのため

core/ を Ink と React から切り離したのはテストのためである。このアプリの複雑さの大半は外部テキストの解釈と時刻計算にあり、どちらも純粋関数にできる。純粋関数を UI から分けておけば、fixture を使う速いテストで大半を検証でき、TUI の自動テストを書かずに済む。

## 遅い情報を待たない

`launchctl print` はジョブごとに 1 プロセス必要で、全ジョブ分を待つと起動が数秒止まる。plist と `launchctl list` は一瞬で揃う。そこで、まず不完全な一覧を出し、詳細は後から上書きする。起動直後に必要なのはどのジョブがあるかであり、run count などの詳細は後でよい。

再取得も同じ方針で、ポーリング中は前回の表示を残したまま差し替える。数秒ごとに一覧が空白になると操作できないためである。表示内容が裏で入れ替わる以上、選択の識別子に index は使えない。選択を label で追従するのはこのためである。

## launchctl の並列を制限する

ジョブ数ぶんの print を無制限に並列発行すると、launchd 側の応答が遅れてタイムアウトが連鎖する。監視ツール自身が launchd を詰まらせないよう、同時実行を 8 に制限している。

## 正確に出せない情報は近似と明示して出す

StartInterval の次回実行時刻は計算できない。launchd は前回実行から N 秒後に発火するが、前回実行時刻を外部から取得する手段が無いためである。空欄にするより now + N を出すほうが役に立つので、近似であることを README に明記した上で表示する。

stdout と stderr のログを時系列にマージしないのも同じ理由による。行にタイムスタンプがある保証が無く、正しい順序は復元できない。誤った順序をそれらしく表示するより、ファイルごとに分けて出す。

## 確認プロンプトは戻せない操作だけに付ける

y/n 確認を付けたのは bootout と kill だけで、基準は可逆性である。kickstart や enable/disable は 1 キーで元に戻せる。bootout は plist のパスを知らないと戻せず、kill は実行中の処理を失わせる。確認を増やしすぎると常に y を押す癖がつき確認の意味が無くなるため、対象を絞った。

## 状態遷移は reducer で適用する

状態遷移は「新しい値」ではなく「操作」として dispatch し、現在値への適用は reducer 側で行う。キー入力は複数キーが 1 チャンクで届くことがあり、そのときハンドラが持つ state は再レンダリング前の古い値なので、「現在値 + 入力」を計算してから dispatch すると 2 打鍵目以降が消える。フィルタ編集が append / backspace の相対操作なのはこのためである。

## 仕様は目的で解釈する

SPEC と実装が字面上ずれている箇所は、SPEC の目的を優先した結果である。

**一覧の範囲**: `launchctl list` は 400 件超のジョブを返すが、一覧は plist を持つジョブに絞った。このアプリの目的は自分が管理する LaunchAgents を見ることであり、Apple 内部の XPC サービスを並べても邪魔になるだけである。SPEC のスコープ定義と 100 ジョブ想定の非機能要件も、この読み方と一致する。

**バイナリ plist**: SPEC は plutil フォールバックを指定しているが、plutil は macOS 専用で、Linux で走る CI ではその経路を検証できない。ライブラリのバイナリパーサを先に使い、plutil は最終フォールバックに回した。指定された手段より、要件を CI で検証できる状態を優先した。

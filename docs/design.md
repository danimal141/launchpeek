# launchpeek 設計思想

本書は、コードや [SPEC.md](../SPEC.md) を読んでもわからないこと、つまり実装の裏にある判断とその理由だけを記す。何がどう実装されているかはコードを読めばよい。

## 信頼できない入力の上に建てる

設計全体を規定する制約は、launchd に状態取得の公開 API が無いことである。すべての情報源は `launchctl` の出力テキストと plist であり、前者の形式を Apple は保証していない。

そこで「パースの失敗は正常系」と位置づけた。未知の行や取れない項目は macOS のバージョン差で日常的に起きるものとして扱い、エラーではなく「情報が無い」状態として UI まで運ぶ。例外で落とすのは、形式が安定した API を持つシステムでのみ許される贅沢だと考えている。この方針の帰結として、パーサの正しさは仕様書ではなく実出力の採取（fixture）でしか担保できない。形式が変わったらテストを直すのではなく fixture を足して追随する、という運用を前提にしている。

## テスト境界がレイヤ境界を決める

core/ を Ink と React から切り離したのは、アーキテクチャの美学ではなくテストの都合である。このアプリの複雑さはほぼすべて「外部テキストの解釈」と「時刻計算」にあり、どちらも入出力が値だけの純粋関数にできる。純粋関数にできる部分を UI から引き剥がしておけば、fixture を食わせる速いテストで検証範囲のほとんどを覆え、TUI の自動テスト（遅く、壊れやすい）を書かずに済む。UI テストを書かないという SPEC の既定は、この分離を守っている限りにおいて成立する。

## 遅い情報を待たない

`launchctl print` はジョブごとに 1 プロセス必要で、全ジョブ分を待つと起動が数秒止まる。一方、plist と `launchctl list` は一瞬で揃う。そこで「不完全でも即座に見せて、正確な情報で上書きする」ことを取得フローの基本形にした。ユーザーが最初の 1 秒で欲しいのはジョブの顔ぶれであって run count ではない、という優先順位の判断である。

同じ判断は再取得にも適用している。ポーリング中も前回の表示を差し替えずに残すのは、一覧が数秒ごとに空白になるアプリは操作対象として信用できないからである。この「常に何かが表示されている」状態を守るために、選択の同一性を画面上の位置（index）ではなくジョブの同一性（label）で追跡する必要が生まれた。表示内容が裏で入れ替わる設計を選んだ時点で、index は選択の識別子として使えない。

## launchd を殴りすぎない

launchctl の同時実行を制限しているのは、このアプリが監視対象そのものを詰まらせては本末転倒だからである。ジョブ数ぶんの print を無制限に並列発行すると、launchd 側の応答が遅れ、タイムアウトが連鎖する。管理ツールは管理対象より軽くあるべき、という原則の具体化である。

## 正確にできないものは、正確でないと明示して出す

StartInterval の次回実行時刻は原理的に計算できない。launchd は「前回実行から N 秒後」に発火するが、前回実行時刻を外部から取得する手段が無いためである。選択肢は「表示しない」か「上界の近似（now + N）を出す」の 2 つで、後者を選んだ。「遅くともこの時刻までには来る」という情報は空欄より役に立ち、近似であることは README に明示すれば足りる。取得できない情報を取得できるかのように見せない、ただし有用な近似まで捨てない、という線引きである。

同じ理由で、stdout と stderr のログを時系列にマージしない。行にタイムスタンプがある保証が無い以上、正しい順序の復元は原理的にできず、それらしく混ぜると「正確に見える嘘」になる。ファイルごとに分けて出すのは機能不足ではなく、嘘をつかないための選択である。

## 破壊的操作の基準は「戻せるか」

確認プロンプトを bootout と kill だけに付けたのは、危険度ではなく可逆性で線を引いたからである。kickstart や enable/disable は逆操作が 1 キーで自明に存在する。bootout は plist のパスを知らなければ戻せず、kill は実行中の処理そのものを失わせる。誤操作した本人がその場で回復できるなら確認は不要、できないなら確認を挟む。確認を増やしすぎると全部 y を押す癖がつき、確認自体が無意味になる、という考えがこの線引きの背後にある。

## 状態遷移は reducer に閉じ込める

連続して起きうる状態遷移は「新しい値」ではなく「操作」として dispatch し、現在値への適用は常に reducer 側で行う。キー入力は複数キーが 1 チャンクで届くことがあり、ハンドラが閉じ込めた state は再レンダリング前の古い値なので、「現在値 + 入力」を計算してから dispatch する方式は同一チャンク内の 2 打鍵目以降を握り潰すためである。フィルタ編集が append / backspace という相対操作なのはこの原則の適用である。

## 仕様は目的で解釈する

SPEC と実装が字面上ずれている箇所は、いずれも SPEC の目的を優先した結果である。

**一覧の範囲**: `launchctl list` は 400 件超のジョブを返すが、一覧は plist を持つジョブに絞った。このアプリの目的は「自分が管理する LaunchAgents のダッシュボード」であり、Apple 内部の XPC サービスで画面を埋めると目的を損なう。SPEC のスコープ定義と 100 ジョブ想定の非機能要件を、この目的の表明として読んだ。

**バイナリ plist**: SPEC は plutil フォールバックを指定するが、plutil は macOS 専用で、Linux の CI ではその経路をテストできない。ライブラリのバイナリパーサを優先し plutil を最後の砦に回したのは、「バイナリ plist を読める」という要件の検証可能性を CI に載せるためである。手段の指定より、検証できる状態を保つことを優先した。
